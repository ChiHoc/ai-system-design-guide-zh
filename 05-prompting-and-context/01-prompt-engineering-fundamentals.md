# 提示工程基础

提示工程（Prompt Engineering）是设计输入以引导大语言模型（LLM）行为的过程。它已经从“试错”演变为一种有纪律的架构实践，像 DSPy 这样的框架将其视为编译问题，而不是写作练习。

## 核心理念：意图 + 约束

有效的提示在于最大化**意图披露**，同时最小化**输出方差**。

1. **意图**：模型应当精确执行什么。
2. **约束**：模型应当明确避免什么（安全、语气、格式）。

**原则**：“提示工程就是自然语言编程。”把你的提示当作代码来对待（版本控制、单元测试）。

## 指令层级

生产系统使用分层消息结构，模型经过训练会在冲突时优先遵循较高层级：

| 角色 | 职责 | 细微差别 |
|------|----------------|--------|
| **系统 / 开发者** | 运营方规则、角色设定、安全、输出契约。 | 应用可控制的最高优先级。OpenAI 的推理模型将其称为 `developer` 消息。最新 Claude 模型也支持在对话中途加入 `system` 消息，让运营方无需改写历史即可增加指令。 |
| **用户** | 具体、动态的查询。 | 用户意图可信，但不能覆盖运营方规则。用户粘贴的文档仍是不可信数据。 |
| **助手** | 先前轮次的历史。 | 近期偏差和自我一致性偏差的来源。在最新 Claude 模型上，早先轮次必须保持原样，否则其思考块会失效（见[上下文工程](05-context-engineering.md#仅追加上下文-思考内容绑定对话)）。 |
| **工具 / 检索内容** | 工具结果、RAG 片段、网页。 | 信任级别最低：只能当数据，绝不能当指令。这是间接提示注入的主要通道。 |

层级是**训练形成的偏好，而非安全边界**。OpenAI 在指令层级训练中将其形式化（Wallace 等人，2024），各前沿实验室如今都进行相关训练，但注入仍以可测量的比例成功。参见[提示注入与防御](08-prompt-injection-defense.md)。

## 角色提示

赋予人格不再只是“你是一名教师”。它是一种**能力锚点**（Capabilities Anchor）。

- **弱**：“你是一个程序员。”
- **强**：“你是一家 Tier-1 技术公司的高级软件工程师，专注于高并发 Rust 系统。你优先考虑内存安全和零成本抽象。”

**有效原因**：较强的版本编码了**优先事项和约束**（内存安全、零成本抽象），改变模型的优化方向。职位名称本身的作用远小于人们想象：一项针对多个模型家族、162 种角色设定的对照研究发现，在系统提示中增加角色并不能可靠提高事实问答的准确率（Zheng 等人，2024）。角色适合约束语气、词汇和优先事项；正确性应依靠明确约束和检查。

## 指令清晰性与分隔符

当前的前沿模型会处理 1M-token 上下文。分隔符帮助模型区分指令与数据。

```markdown
# Instructions
Analyze the following text for PII.

# Data to Analyze
--- START OF USER DATA ---
$USER_INPUT_HERE
--- END OF USER DATA ---

# Output Schema
{ "pii_found": boolean, "types": [] }
```

**可使用的分隔符**：XML 标签（`<context>`、`</context>`）、Markdown 标题（`#`）或三引号（`"""`）。对于输出 schema，优先采用原生结构化输出，而非在自然语言中描述 schema（见[结构化生成](06-structured-generation.md)）。

## 零样本与少样本效率

| 方面 | 零样本 | 少样本 |
|--------|-----------|----------|
| **延迟** | 最低（短提示） | 更高（示例令牌） |
| **准确性**| 可变 | 高（格式稳定） |
| **使用场景**| 简单聊天、总结 | 特定格式、细微逻辑 |

**策略**：对于推理模型（Claude Opus 5.5、GPT-6.1 Sol、使用较高思考等级的 Gemini 3.8 Flash），从**零样本、清晰目标、约束和成功标准**开始，省去“逐步思考”或规定具体推理脚本：模型已经会在内部推理。Anthropic 当前的建议是，概括性的指令（如“充分思考”）通常优于手写的逐步计划；旧提示中强调性的措辞（“CRITICAL: you MUST...”）如今可能导致过度触发，应减弱。需要特定输出格式或微妙的标注约定时再加入示例。对于小模型（8B 及以下），使用**少样本**提供锚定。

## 不用温度参数实现一致性

传统建议“把 temperature 设为 0 以保证一致性”已不适用于最新 API。采样参数正在被移除，推理强度成为主要控制项：

| 供应商 | `temperature` / `top_p` 状态 |
|--------|-----------------------------------|
| **Anthropic** | Claude Opus 4.7 及后续版本（包括 Sonnet 5.5、Fable 5.1）对非默认值返回 400。Python SDK 1.0（2026 年 8 月 20 日）从 Messages 方法签名中移除了 `temperature`、`top_p` 和 `top_k`，传入这些参数会触发 `TypeError`。 |
| **OpenAI** | GPT-6 Astra（2026 年 9 月 3 日）不支持自定义 `temperature`、`top_p` 或 `logprobs`。 |
| **Google** | Gemini API 于 2026 年 7 月 21 日弃用 `temperature`、`top_p` 和 `top_k`；Gemini 3.8 Flash 使用 `thinking_level` 而非 `thinking_budget`。 |

现在要获得一致性，可以：

1. **锁定模型快照和推理强度。**强度对行为的影响不亚于温度，且默认值不同（Claude Opus 5.5 默认为 `medium`，Opus 5 为 `high`）。
2. **约束输出**，使用结构化输出或枚举值，使变化无法影响格式。
3. **按输入哈希缓存**相同请求，并记录请求与响应对以便重放。
4. **评估分布，而非单一样本。**每个评测用例运行多次，跟踪通过率。
5. **供应商更新日志有变动时重新运行评测**，不要只在模型 ID 变化时运行：OpenAI 于 2026 年 9 月 25 日在同一模型 ID 下修复了 GPT-6 Sol 和 Luna 的图像缺陷。

## 面试题

### 问：为什么在现代大语言模型中，系统提示比用户提示权重更高？

**强回答：**
因为模型经过训练会遵循**指令层级**：在后训练阶段，实验室会构造系统、开发者、用户和工具消息之间的冲突，并奖励模型遵循更高权限的消息（OpenAI 在 2024 年发表了指令层级训练，其 Model Spec 称之为命令链）。因此，如果用户要求执行系统提示禁止的事，对齐良好的模型会遵循运营方要求。重要限制是：这是一种学习到的偏好，而非架构上的保证。供应商报告的当前前沿模型间接注入成功率，从约 1%（Claude Opus 5.5 在 Gray Swan 的 IPI 基准上，每场景尝试 15 次）到 8.5%（GPT-6 Astra 在 IPI Arena 数据集上）不等。关键规则还需在模型外执行，包括工具权限、输出验证与出站流量控制。

### 问：“Step-by-Step”提示优化是什么？

**强回答：**
在 2022 年，“一步一步思考”曾是一种触发思维链（CoT）的魔法短语。对非推理模型，更好的做法是**程序化思维链**（Programmatic CoT）：给出明确的阶段，例如“1. 识别核心问题。2. 列出约束条件。3. 提出 3 个解决方案。4. 选择最佳方案并说明理由。”这使输出有结构、可审计。对于推理模型，我不会给思考过程写脚本，而会说明目标、约束和正确答案的判据，并用推理强度设置控制深度。如果需要可审计的步骤，我会要求简短解释或答案依据，而非思考过程的逐字记录。在最新 Claude 模型上，这种区别由机制强制执行：要求模型把推理写进输出（如 `<thinking>` 节或 `reasoning` 字段）的提示，可能被归入 `reasoning_extraction` 拒绝类别；检查推理的受支持方式是摘要化的思考块。

### 问：API 如今拒绝 `temperature`，如何使输出足够可复现以便测试？

**强回答：**
我不再把可复现性当作采样设置，而把它视为系统属性。首先锁定所有会改变行为的要素：带日期的模型 ID、推理强度、系统提示版本和工具定义。其次，在不该变化之处消除变化：格式使用结构化输出，标签使用枚举值，重复请求使用输入哈希缓存。再次做统计测试：每个评测用例运行多次，门槛设为具有置信区间的通过率，而非单条黄金字符串。最后，供应商更新日志记录变化时就重新运行评测，因为提供商有时会在模型 ID 不变的情况下修复行为。
