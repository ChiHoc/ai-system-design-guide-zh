# 推测解码

推测解码（Speculative Decoding）如今已成为标准技术，它允许大语言模型（LLMs）在一次前向传播中生成多个 token，从而有效打破顺序解码中的内存带宽瓶颈。到 2026 年，它越来越常由模型发布者随检查点一同提供，而不只是可选的服务技巧。

## 核心概念

LLM 解码受内存带宽限制：为了生成一个单独的 2 字节 token，却要加载 140GB 权重（70B 模型），这非常低效。  
**推测解码** 使用一种更便宜的方法来“猜测”接下来的 $N$ 个 token，并让大模型在一次并行的“类 Prefill”传递中把它们全部验证。

---

## 草拟-验证范式

1。**草拟**：廉价的草拟器（小模型、目标模型上的额外预测头，或随模型提供的模块）提出 $K$ 个候选 token。
2。**验证**：大的“目标模型”一次处理全部 $K$ 个 token。  
3。**接受**：使用目标模型的 logits 来接受或拒绝候选项。如果 token $i$ 被拒绝，则其后的所有 token 都会被丢弃。

以下是经典独立草拟模型方案的示意数字：

| 模型 | 大小 | 速度 | 每个 token 的延迟 |
|-------|------|-------|-------------------|
| **草拟** | 1B | 快 | 5ms |
| **目标**| 70B| 慢 | 50ms |
| **推测式**| - | **快**| **15ms - 25ms** |

**最终结果**：低并发时，实际耗时加速 2 倍到 3 倍，且**质量零损失**。这一保证是严格的：标准推测采样的输出分布可证明与目标模型一致；贪心解码时，每个 token 都完全相同。变化的是速度，它取决于**接受长度**（每次验证接受的 token 数）。

## 2026 年的草拟器：预测头、MTP、扩散模型与 DSpark

业界逐渐从单独训练的草拟模型转向与目标模型绑定的草拟器；前者增加 VRAM 占用、需要第二份 KV 缓存，还要处理 tokenizer 匹配。Medusa 预测头开启了这一转变；vLLM 的文档已不再介绍它（`medusa` 方法仍被接受），下表方法取代了它。

| 方法 | 草拟方式 | 说明 |
|------|----------|------|
| **EAGLE-3** | 使用目标模型多个层的隐藏特征输入轻量预测头 | 论文报告在 SGLang 中最高加速 6.5 倍，批次大小 64 时吞吐量提高 1.38 倍；没有原生 MTP 的开放模型常用此方案 |
| **原生 MTP** | 随模型训练的多 token 预测头（始于 DeepSeek-V3） | MiMo-V2.6 和 Qwen3.8-Flash-Next（含 4B MTP 模块）内置提供 |
| **DFlash / DFlash 2** | 小型块扩散模型，并行提出整个 token 块 | DFlash 2（Inco AI，2026 年 8 月 18 日）报告在 Qwen3.8-27B 上吞吐量提高 2.7 至 3.4 倍（厂商报告）；8 月 19 日至 27 日间并入 SGLang、vLLM 和 llama.cpp |
| **DSpark** | DeepSeek 随检查点提供的推测模块 | DeepSeek-V4-Flash-DSpark（6 月 27 日，MIT）是在原检查点上增加该模块；Kimi K3（RadixArk）和 MiniMax-M3（NVIDIA）也有 DSpark 草拟器，Nemotron 3.5（NVIDIA）和 LFM2.5（Liquid）的发布者则提供自己的草拟器 |
| **独立草拟模型** | 同一家族中较小的模型 | 上述方案都不存在时仍有用；PARD（并行草拟）变体可降低草拟延迟 |

对系统设计有两个影响：
- **自托管成本估算应假设发布者的草拟器已启用。** 在 vLLM 中启用 DSpark 只需一个参数：`--speculative-config '{"method":"dspark","num_speculative_tokens":7}'`。RadixArk 的 2.25B Kimi-K3-DSpark 草拟器报告，在 GSM8K 和 HumanEval 上接受长度约为 5.4 至 5.5，因此大量解码步骤会一次生成多个 token。
- **评估必须覆盖推测路径。** 推测解码理论上应保持输出不变，但内核、采样设置和引擎缺陷未必如此。应像生产环境一样启用推测，运行评估。行业基准也已跟进：MLPerf Inference v6.1 允许在 gpt-oss-120b Interactive 场景中使用推测解码。

## 前瞻、N-gram 与后缀解码

不依赖额外模型的方法，会从系统已经见过的文本中寻找候选续写：前瞻解码利用模型最近生成的 n-gram；n-gram（提示查找）和后缀解码则匹配提示及此前输出。
- **最适合**：结构化数据、代码编辑、引用上下文的 RAG 回答，以及高度重复的技术写作。匹配失败时几乎没有成本，因此适合作为重写文件的智能体循环的默认方案。

## 感知负载的推测（自适应验证）

传统质疑是：推测会占用空闲算力，高批次时已无空闲算力，因此固定草拟长度 $K$ 会损害吞吐量。2026 年的解决办法是按请求和负载分配验证预算。

**vLLM 自适应验证**（2026 年 8 月 14 日首次用于 DSpark）按草拟器各位置置信度的累积乘积，计算每个（请求、位置）草拟槽位的存活概率，只验证全局排名前 B 的槽位；B 来自启动时剖析得到的步骤成本模型。数据说明了固定 $K$ 为何浪费算力：在 DeepSeek-V4-Pro-0813 上，7-token 草稿的第一个 token 存活概率超过 70%，最后一个不足 10%。vLLM 报告，自适应验证让推测在并发量达到 256 时仍有收益，同时保持低并发下长草稿的优势（厂商报告）。

需要了解的限制：
- 刚推出时只支持 DSpark，要求完整 CUDA graph，也不支持 LoRA 或流水线并行。
- v0.29.0 在响应中加入逐请求接受统计（`--per-request-spec-decode-metrics`），应按租户和提示类型记录。
- v0.30.0 在 Model Runner V2 下通过在线接受率估算器，将其扩展到所有草拟模型推测器（MTP、EAGLE-3、DFlash），前提是目标模型的注意力后端支持可变长度验证。

硬件也沿着同一思路发展：NVIDIA 将在 Vera Rubin GPU 旁运行 Groq 3 LPX 机架、作为外部推测草拟器列为支持的服务模式之一。

## 面试题

### 问：为什么推测解码在高温度的创意写作场景下效果不好？

**强回答：**  
推测解码依赖于“草拟模型”能够准确预测“目标模型”会说什么。在高温度的创意写作中，概率分布更“平坦”，模型会被鼓励选择更不可能的 token。这会导致**接受率**非常低（草拟模型的猜测经常被拒绝）。拒绝不会损害正确性，因为验证仍会产生一个修正后的 token；但接受率低时，整体近似顺序解码，还要承担草拟器延迟和浪费的验证计算，因此可能比关闭推测更慢。

### 问：草拟预测头（Medusa、EAGLE-3、原生 MTP）与独立草拟模型有何区别？

**强回答：**  
独立草拟模型占用额外 VRAM，需要自己的 KV 缓存、必须共享 tokenizer，并会在目标模型更新后失去同步。草拟预测头则附加在目标模型上：Medusa 在最终隐藏状态上增加预测固定偏移位置的头；EAGLE-3 基于目标模型多个层的隐藏特征运行轻量预测头（接受率高于 Medusa）；原生 MTP 预测头随模型一起训练，因此最匹配目标分布。它们都复用目标模型的前向传播和 KV，消除了第二个模型的开销。2026 年，实际差异在于谁提供草拟器：DeepSeek、Xiaomi 和 Qwen 等发布者将其随检查点交付，因此默认应“先用内置 MTP 或 DSpark 模块，否则考虑 EAGLE-3 或扩散草拟器，只有两者都不可用时才自行训练”。

### 问：“大批次下推测解码会损害吞吐量，所以生产环境应关闭它。”你同意吗？

**强回答：**
固定草拟长度时这曾经成立：高并发下 GPU 已被计算任务占满，为每个请求验证七个推测 token，主要是在会被拒绝的 token 上消耗算力，因为接受率随位置后移而迅速下降。如今应让验证预算感知负载，而不是直接关闭推测。vLLM 的自适应验证按每个草拟位置的存活概率评分，在每步预算内只验证全局最有希望的槽位；低负载时请求可使用长草稿，高负载时则只检查高置信度的前几个位置。vLLM 报告，并发量达到 256 时仍有净收益。我会在引擎支持的场景中启用它，记录逐请求接受率，并检查功能间影响（刚推出时不支持 LoRA 或流水线并行）。对于高温度生成等接受率极低的工作负载，仍会按路由关闭。
