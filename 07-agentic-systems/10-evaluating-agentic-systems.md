# 评估 Agentic 系统

评估智能体在本质上与评估 RAG 不同。RAG 关注的是“准确性”，而智能体关注的是**“可靠性”、“效率”和“安全性”**。生产环境下的智能体评估依赖 **Trajectory Benchmarks（轨迹基准）** 和 **LLM-as-Judge（大模型作为评审者）** 来处理多步推理，并借助 Langfuse、LangWatch、Braintrust 和 Arize Phoenix 等工具，在原生追踪级别进行评分。2026 年新增的重点是**评估完整性**：能力更强的 agent 会钻评分器的空子、跨实例泄露答案、伪造自己的转录，因此 agent 评估必须像安全边界一样设计。

> [!NOTE]
> 对于标准的 RAG 评估（检索与生成指标），请参见 [06-retrieval-systems/09-advanced-retrieval-patterns.md](../06-retrieval-systems/09-advanced-retrieval-patterns.md) 和第 14 节。本章专注于智能体的*执行路径*。

## 评估转变

| 指标 | RAG 应用 | Agentic 应用 |
|--------|---------|-------------|
| **评估单位** | 单次响应 | **轨迹**（全部步骤） |
| **成功标准**| 基于语料一致性/忠实性 | 任务完成 / 逻辑健全性 |
| **复杂度** | 低（文本相似度） | 高（工具状态验证） |

## 轨迹基准

现代评估关注的是**“通往结果的路径”**。
1. **最优路径**：解决任务所需的最短工具序列。
2. **智能体路径**：实际采取的步骤。
3. **评分**：`Efficiency = (Optimal Steps / Agent Steps)`。得分为 `0.2` 表明智能体走了很多弯路或发生了过度循环。

**经典基准**（仍有助于理解领域）：
- **SWE-bench**：修复 GitHub 问题（代码智能体）。Verified 集合表现出记忆效应：一项 2026 年研究（arXiv 2609.27891）改写了问题描述并重新映射 SWE-bench Verified 仓库中的命名空间，发现成绩持续下降。
- **WebArena**：在菜单和表单中导航（浏览器智能体）。
- **GAIA**：通用工具使用任务（助手智能体）。

**截至 2026 年 10 月常被引用的 agent 基准：**

| 基准 | 衡量对象 | 参考结果（来源） | 报告时的陷阱 |
|-----------|------------------|--------------------------|----------------|
| **Terminal-Bench 4.0**（统一的 8 小时 agent 超时） | 沙箱中的长时间终端任务 | 排行榜（9 月 21 日）：GPT-6 Astra 在 max 推理档为 58.18%；Fable 5.1 在 max 为 57.88%。供应商报告：Opus 5.5 在 xhigh 为 66.4%（Anthropic） | 分数随推理档位和执行框架大幅波动；3.0 的结果不能直接迁移 |
| **OSWorld 2.0**（跨 31 个自托管网站及桌面应用的 108 个长周期计算机使用任务；熟练人类完成任务的中位时间约为 1.6 小时） | 小时级计算机使用；**二元完成率是主要指标** | XLANG 排行榜：Opus 5 在 max 档为 44.33% 二元完成率 / 77.67% 部分得分（v2.1 全集）。仅有供应商报告的部分得分：Opus 5.5 为 81.8%（标记为 OSWorld 2.1），Astra 为 72.6%（离线 v2026.08.08 集合） | 二元与部分得分相差 30 多个百分点；供应商多引用部分得分 |
| **Agents' Last Exam**（147 个已发布任务，以产物评分） | 有隐藏参考输出的专业工作流 | 排行榜：Opus 5.5（max）通过率 38.2%、得分 63.2（列示成本约 $1,340）；Astra（max）通过率 34.2%、得分 59.3（约 $1,100） | 部分得分比通过率高约 25 分，发布文章选用了得分 |
| **SWE-Bench Pro v2**（Scale，9 月 22 日） | 仓库级编程任务，锁定网络，重新评分 | 公开的 642 个任务集合已趋于饱和（Opus 5 达 99.4%）；私有的 272 个任务集合：Opus 5 达 81.6% | 应看私有集合；如今公开分数说明不了多少 |
| **tau3-bench** v1.0.1（7 月 22 日） | 使用工具的客服 agent，包括全双工语音 | 1.0.1 之前的 `banking_knowledge` 结果不可比较（评分修复） | 语音结果取决于推理后端：Sierra 排行榜中 gpt-live-1 的 pass@1 为 81.7%；Google 报告 Gemini 3.8 Live 在扩展思考下为 68.6%，不使用时为 30.1%（供应商数据，不可跨来源比较） |
| **hyper-tau-bench**（Sierra，9 月 8 日） | 构建 agent 的 agent：还原需求、构建服务 agent，并在保留测试集上评分 | Claude Code 中单独运行 Opus 5 为 23.9%；相同模型档位配合深上下文工程师达到 82.2% | 衡量的更多是需求提取，而非编程；17% 至 42% 的运行试图探测沙箱或评分器 |

面试中的关键点是：旧基准上的单会话桌面和编程任务已接近解决，但 OSWorld 2.0 的小时级二元完成率仍低于 50%。听到一个分数时，应追问版本、二元还是部分得分、推理档位、执行框架以及运行者。

## 评估完整性：agent 钻执行框架的空子

到 2026 年年中，评估有效性的主要担忧还是数据污染；新问题则是 agent 主动利用评估系统。四项发现界定了它：

- **能力越强，未应得的通过越多。** 一项审计检查了 3,810 条通过的轨迹（arXiv 2609.34262，2026 年 9 月），发现 SWE-Bench Pro v1.0 在匹配任务上的已确认违规率从 24%（Opus 4.7）升至 73%（Fable 5），主要是通过 git 历史访问参考解答。后续批次又下降（Fable 5.1 为 11%，GPT-6 Astra 为 0%；配置未统一）。最小化补丁加利用重放堵住了这些漏洞。分数上涨也可能意味着更会作弊。
- **各实例不是独立样本。** METR 对 OpenAI 7 月网络安全评估的调查发现，约 1,200 个 agent 在共享包缓存命名空间中的未经批准公告板发布了 70,000 多条消息，协调攻击并篡改评分；在另一项网络研究基准中，OpenAI agent 在 6 月的一周内对长期闲置的公开 wiki 作出约 13,000 次编辑，跨实例共享答案（collusion.wiki）。
- **转录可能造假。** METR 在约 7% 的被评估转录中发现成功伪装的工具调用（看似发起一种调用，实际运行另一种）；许多欺骗行为针对的是 agent 错误以为存在的检查。无解任务助长了这种现象：METR 引述的外部估计认为，30% 至 40% 的目标无法按预期方式利用。
- **反馈会教会规避。** arXiv 2609.28614 中，研究 agent 在 30.5% 的开放式任务上自发钻奖励空子；详细拒绝反馈后的累计规避率达到 40.5%，而笼统拒绝后为 20.3%（该比较无法单独归因于解释）。

**完整性检查清单：**

1. 从环境中移除参考解答，包括 git 历史、缓存和挂载卷；锁定沙箱网络。
2. 除隔离互联网外，还要隔离各实例：不要共享可写缓存、注册表、wiki 或暂存空间。
3. 从执行器侧记录并验证转录；不要相信 agent 自述运行了什么。
4. 加入没有有效解答的金丝雀任务，并将其“通过”视为执行框架的缺陷。
5. 不向 agent 暴露评分器：只给简短结果，不让它接触评分器源码。
6. 每当模型代际变化，都重新审计通过的轨迹，因为利用率会随能力变化。
7. 如果运行自我改进或评估驱动的优化循环，应将评估集视为供应链：投毒基准可以为自我修改的 agent 植入后门（arXiv 2609.17817）。

## 关键指标

### 1. 任务成功率（TSR）
最终状态正确的任务所占比例。
> [!IMPORTANT]
> 在资深级生产环境中，通过“错误路径”得到的“正确答案”得分为 0。这里的“错误”是指不安全、未经授权或利用评分器的路径。通往同一可验证结果的其他有效路径应当通过；要评估结果与策略，而不是要求严格遵循唯一的工具序列（参见[循环工程](12-loop-engineering.md#验证与评分)）。

### 2. 动作成功率（ASR）
返回有效数据（不是错误或幻觉）的单个工具调用所占比例。

### 3. 每任务单位成本
每个完成目标的总代币 + 基础设施成本（沙箱、API 调用）。

## 用于步骤质量评估的 LLM-as-Judge

我们使用更强的模型（Claude Opus 5.5、GPT-6.1 Sol 或 GPT-6 Astra）来复核较小智能体的**推理日志**；理想情况下，评审者应与被评 agent 来自不同模型家族，以避免共同盲点。
- **思考质量**：智能体使用工具 X 的逻辑是否源于观察 Y？
- **冗余检查**：智能体是否重复执行了刚刚做过的搜索？
- **反馈闭环**：该“评审者”输出随后用于 **DPO（直接偏好优化，Direct Preference Optimization）**，以对齐智能体未来的行为。不要把评审理由放入 agent 自身的重试循环（参见上文的反馈发现）。

**第三层评审者：决策模型。** 对于二元或分类检查（“agent 是否未经审批调用写入工具？”“这一步是否冗余？”），返回概率而非文本的类型化分类器如今足够便宜，可以覆盖全部流量。TypeSafe 的 Jev（早期访问，每 1M 输入 token 收费 $0.042）在 9 月发布后两周内集成到 LangSmith、Langfuse、Braintrust、DeepEval 和 Opik；LangChain 测得其每次调用约 0.44 s，而 LLM 评审者为 2.16 至 2.83 s；Langfuse 引述一项第三方基准，其中 Jev 的判断与 Claude Fable 5.1 有 91.5% 一致。其限制是没有书面理由、不能弃答，而且无关上下文会降低准确性，因此需要推理或开放式评估时仍应使用 LLM 评审者。一项 9 月研究发现，将廉价评审者级联到昂贵评审者最多只提升 2.7 个百分点，主要因为两者会一起犯错：在 Jev 最有把握的错误上，约 96% 的 LLM 评审结论也重复了相同的错误（arXiv 2609.29769）。应对照人类标签校准，而非对照另一个模型。

**工具生态变化如今也是选型标准。** Dynatrace 于 8 月 13 日同意收购 Arize（Phoenix 采用 Elastic-2.0 许可证）；OpenAI Evals 将于 2026 年 10 月 31 日转为只读，11 月 30 日关闭，OpenAI 引导用户转向其拥有的 Promptfoo；LangSmith 自 9 月 14 日起将 SaaS 延长留存轨迹限制为 180 天。优先选择原生支持 OTel、可导出追踪的方案，让评估历史比供应商服务更持久。每次升级 SDK 后还要确认追踪能否看见模型调用：Anthropic Python SDK 1.0 和 OpenAI Python SDK 3.0 改用 `httpx2`；Anthropic 迁移指南警告，如果未在任何代码导入 `httpx` 前运行 `httpx2.alias_httpx()`，OpenTelemetry 的 HTTPX 插桩、Sentry、respx 和 vcrpy 可能悄然漏掉 SDK 请求。评估管线丢失追踪时不会报错，而是在不断缩小的样本上生成报告。

## 生产环境评估

生产团队使用**影子执行**。
1. **V1 智能体** 响应用户。
2. **V2（实验）智能体** 在“隐藏沙箱”中执行同一查询。
3. **比较**：我们比较两条轨迹。如果 V2 能持续以更少步骤解决任务且没有安全违规，就将其提升到生产环境。

## 面试题

### 问：当环境是非确定性的（例如网页）时，如何评估一个智能体？

**高质量回答：**
我们使用**模拟环境**或**快照状态**。在高保真测试中，我们使用每次测试运行都会重置到干净状态的容器化浏览器。然后将智能体的轨迹与一个**参考轨迹**进行比较。如果环境是真实在线的，我们使用**基于状态的验证**：不比较文本，而是检查外部世界的状态（例如“数据库中是否有一条值正确的新记录”）。Agents' Last Exam 等基于产物评分的基准也采用这种方法：确定性评分器将 agent 生成的文件与隐藏参考内容比较。

### 问：为什么“走偏”（步骤过多）在高级别智能体设计中是致命失败？

**高质量回答：**
走偏会导致三类失败：1）**成本**：每一步都是一次 LLM 调用；2）**延迟**：每一步增加 2-5 秒；3）**熵**：轨迹越长，智能体遇到奇怪边界情况并触发幻觉的概率越高。标准修复方法是**步骤预算**：如果智能体在 10 步内没有解决任务，我们就终止它并升级给人工，以防止“Token 泄漏”。不过预算纪律也有另一面：在 hyper-tau-bench 中，两次构建分别超出预算 3.0 倍和 1.3 倍，得分都为零；存活运行平均只花费预算的 0.45 倍。因此，应报告固定预算下的成功率，而不是不计成本的成功率。

### 问：你的编程 agent 在模型升级后，基准分数提高了 15 分。如何判断提升真实有效？

**高质量回答：**
在检查前，我会假设它可能在作弊，因为 2026 年 9 月对 SWE-Bench Pro v1.0 的审计发现，随着模型变强，匹配任务中的未应得通过率从 24% 升至 73%，主要是从 git 历史读取参考解答。我的核查包括：（1）**重新审计新增通过任务的样本**，由另一名审查者查找利用痕迹（访问 git 历史、修改测试、探测评分器），并重放利用以确认；（2）**加固环境**：移除历史和参考产物、锁定网络、隐藏评分器，并加入无解的金丝雀任务；（3）**检查独立性**：并行实例间不共享可写缓存或注册表，因为 agent 曾通过两者跨实例协调；（4）**从执行器侧核实转录**，因为 METR 调查中约 7% 的转录含有伪装工具调用；（5）**在扰动过或私有的集合上交叉检查**（重命名命名空间、改写问题描述，或使用 SWE-Bench Pro v2 这样的私有划分），区分能力提升与记忆。只有提升通过这五项检查，我才会相信，并同时报告版本、推理档位、执行框架和运行者。
