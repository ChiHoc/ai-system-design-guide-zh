# 记忆架构

LLM（大语言模型，Large Language Model）记忆已经从“历史缓冲区”演进为**三层认知架构（Three-Tiered Cognitive Architecture）**。这一层级模仿人类认知系统（L1-L3），以平衡速度、成本和回忆容量。生产环境中的智能体（agent）技术栈如今更倾向于使用专用记忆层（Mem0、Zep、Letta、Cognee）或托管式 agent 平台的记忆功能，而不是自行从头实现。2026 年，向量和图谱之外又加入了第三种底层载体：以 git 版本化、按路径导航的**普通文件**。从 agent 视角看增加程序记忆的四层结构，可参见[智能体记忆与状态](../07-agentic-systems/05-agent-memory-and-state.md)。

## 三层层级

| 层级 | 类型 | 人类类比 | 技术实现 | 延迟 |
|------|------|----------|----------|------|
| **L1** | 工作记忆 | 即时关注焦点 | 上下文窗口 / KV Cache（键值缓存） | <50ms |
| **L2** | 情景记忆 | 过往经历 | 向量数据库 / 原始轨迹日志 | 100-300ms |
| **L3** | 语义记忆 | 通用知识 | 事实存储（Mem0）、时序图谱（Zep/Graphiti）、SQL、记忆文件 | >500ms |

---

## 第一层：工作记忆（L1）

L1 是模型的**当前活跃焦点**。  
- **上下文窗口**：当前前沿模型约为 1M token（Claude Opus 5.5 和 Sonnet 5.5 为 1M，GPT-6.1 Sol 为 1.05M，Gemini 3.8 Flash 为 1,048,576）；开放权重模型为 128K 到 1M。
- **KV Cache**：存储预计算键和值的 GPU“内存”。
- **管理策略**：**滑动窗口**、**压缩**和**前缀缓存**（vLLM/PagedAttention、SGLang RadixAttention）。
- **冗余说明**：我们只在 L1 中保留最近的轮次和关键系统指令。

---

## 第二层：情景记忆（L2）

L2 存储本次会话或与该用户的过往会话中“之前发生了什么”。
- **存储**：向量数据库（Pinecone、Weaviate、Qdrant），原始日志放在对象存储中。
- **检索**：语义搜索。如果用户问“我们上周二聊了什么？”，L2 会提供答案。
- **模式**：**经验回放**。智能体检索过去成功的轨迹来指导当前决策。

---

## 第三层：语义记忆（L3）

L3 存储**持久事实**和**已学习规则**，直到有新信息取代它们。
- **知识图谱**：存储关系，例如 `User` -- `WORKS_FOR` --> `Company_X`；如果需要回答“这是什么时候变成事实的”，还应记录有效时间区间（Zep/Graphiti）。
- **Mem0**：用于抽取事实（例如“User likes Dark Mode”）并跨会话提供的开源库和托管平台。自 v2.0.0（2026 年 4 月）起，它将事实存入用户的向量存储，并维护并行的实体索引，而非图数据库。
- **真值锚定**：当 L1 和 L2 提供冲突信息时，L3 充当“基准真值（Ground Truth）”；但前提是在某处解决冲突（写入时、定时巩固任务中，或读取时）。

---

## 基于文件的记忆：按路径检索

2026 年最大的架构变化是把记忆存为**agent 通过普通工具读写的文件**，而不是靠嵌入相似度检索的数据库行。

| 系统 | 工作方式 |
|--------|--------------|
| **Letta MemFS** | Letta 于 2026 年 8 月 16 日归档其 MemGPT 时代的服务器。所有 agent 现在都使用 MemFS：长期记忆是一个带 YAML frontmatter 的 Markdown 文件 git 仓库。记忆根目录下的文件每轮加载到系统提示词；含独立 `MEMORY.md` 索引的目录则留在上下文之外，通过索引指路。默认不使用向量索引。 |
| **Claude memory tool 与 Managed Agents 记忆存储** | 模型通过工具读写 `/memories` 目录；Managed Agents 为每个会话挂载存储，自托管沙箱也于 2026 年 8 月 19 日获得记忆存储能力。 |
| **编程 agent** | `CLAUDE.md`、`AGENTS.md` 和技能文件：人类可以在拉取请求中审查的项目记忆。 |

**为何适合 agent**：人类能阅读、比较差异和审查；git 免费提供版本管理与回滚；agent 能按结构（索引文件、目录）导航，而不必寄望于正确片段的相似度得分最高。**不适合的场景**：规模庞大或频繁变化的事实集、跨用户汇总，以及在数千段经历中模糊召回，这些仍是向量检索的用武之地。

## 记忆巩固模式

记忆通过**巩固**在各层之间迁移：
1. **抽取**：会话结束时，LLM“审阅者”从 L1 中抽取事实。
2. **索引**：事实被存入 L2（作为向量）和 L3（作为事实、图谱边或记忆文件）。
3. **衰减**：未被强化的旧情景记忆会归档到冷存储或被删除；提升到 L3 的事实应被新事实取代，而不是悄然衰减。

如今面试官会进一步追问巩固在**何时**运行：

| 时机 | 示例 | 取舍 |
|--------|---------|----------|
| **写入时** | Mem0 v2：每次 `add()` 执行一次仅 ADD 的抽取调用 | 读取便宜；抽取错误会固化 |
| **休眠时** | Anthropic Dreams（研究预览）、Mem0 的 Dream（付费方案） | 不占用请求路径；两次运行之间可能过时 |
| **读取时** | Just-in-Time Memory（arXiv 2609.27334）：保留原始轨迹，针对任务整理 | 成功率比最强的写入时基线高 3.9 至 16.3 个百分点；整理成本转移到读取时 |

记忆并非越多越好：在专门诱发记忆陷阱的 MemTrapBench（arXiv 2608.20202）任务中，测试过的所有记忆策略都不如不使用记忆，因为即便记忆正确且相关，也会造成推理固着。应对记忆注入实施门控，并分别评估使用与不使用记忆时的任务成功率。

## 面试题

### Q: 为什么不直接用 1M token 的上下文窗口来承载全部记忆（L1-L3）？

**标准答案：**
虽然可行，但这在**经济上和认知上都低效**。  
1. **成本**：每轮向 Claude Opus 5.5 输入 1M token，未缓存时需 $4.00，即使完全缓存也需 $0.20；使用检索上下文的 10K-token 调用只需 $0.04。缓存缩小了差距，但没有消除它；而 OpenAI 在输入超过 272K token 后，会按长上下文费率计费整个请求。
2. **注意力稀释**：即使是“长上下文”模型，“中间遗忘（Lost in the Middle）”和上下文腐化仍然存在。如果上下文中塞满无关的历史轮次，模型对**当前**任务的推理会退化。
3. **延迟**：TTFT（Time to First Token，首个 token 时间）随未缓存上下文规模增大而增加，长上下文中的逐 token 解码也更慢。
高级别架构会使用**策略性检索**，让上下文窗口保持精简且聚焦。

### Q: 如何处理第三层（全局语义记忆）中的“隐私泄露（Privacy Leakage）”？

**标准答案：**
第三层（语义记忆）必须按**命名空间分片**。每个用户或组织在向量数据库和知识图谱中都会获得唯一的 `namespace_id`。我们在数据库层实现**RLS（Row Level Security，行级安全）**。此外，我们在巩固步骤中使用**PII 脱敏层**，以确保敏感数据（passwords、PII）永远不会从临时的 L1 上下文进入持久化的 L3 知识存储。如果要求连平台运营者都无法读取记忆，参考设计是由客户端持有密钥，并在硬件飞地中处理：Google 于 2026 年 9 月 23 日描述了 Private AI Compute 平台的服务端记忆计划（未给产品时间表），其中存储密钥只保存在用户设备上，经远程证明的飞地按请求解密并重新加密；服务器软件会发布到防篡改的公开记录中，供设备在发送数据前验证。这与 Apple Private Cloud Compute 的模式相同。

### Q: 什么时候会把 agent 记忆存为文件，而不是向量数据库？

**标准答案：**
当记忆**规模小、经过整理且需要人类监督**时，使用文件：例如项目规范、用户偏好、操作流程和决策。几百个带索引的 Markdown 文件适合 agent 按路径导航；每次改动都是可审查的 git diff，回滚只需 revert。因此 Letta 将所有 agent 转向 git 支撑的 MemFS，编程 agent 也趋同使用 `CLAUDE.md` 和 `AGENTS.md`。当记忆**规模大、持续追加且需要模糊召回**时，使用向量：例如数千段过往对话或轨迹，无法事先知道哪段重要。大多数生产系统最终两者兼用：语义层和程序层用文件，情景层用向量（或保留原始日志，在读取时整理）。文件还有一个运维问题：根据 GDPR 删除用户数据时，必须清除 git 历史，而不能只删除当前提交中的内容。
