# 语义缓存（Semantic Caching）

缓存已从精确字符串匹配演进为**语义匹配（Semantic Matching）**。语义缓存复用“等价”查询的完成结果，在命中时把延迟从秒级降至毫秒级。节省多少完全取决于流量的重复程度：FAQ 式客服流量可能大幅受益，开放式 agent 工作则很少重复。它也不同于供应商的提示词缓存：后者降低重复*输入*的价格，而非跳过调用。

## 精确缓存 vs. 语义缓存

| 特性 | 精确缓存（Redis/Memcached） | 语义缓存（RedisVL/Qdrant） |
|---------|-------------------------------|---------------------------------|
| **键** | 哈希后的查询字符串 | 查询 embedding 向量 |
| **匹配** | 100% 字符串完全一致 | 余弦相似度 > 阈值 |
| **效率** | 低（轻微拼写错误会破坏缓存） | 高（理解意图） |
| **风险** | 无 | 语义漂移（返回错误答案） |

## 语义缓存与供应商提示词缓存

两者解决不同问题，也可以叠加使用：

| | 语义缓存（自有） | 供应商提示词缓存 |
|---|------------------------|-----------------------|
| **复用内容** | 整个响应 | 重复输入前缀的 KV 缓存 |
| **节省内容** | 整次 LLM 调用：输入、输出和延迟 | 仅输入成本和预填充时间 |
| **折扣** | 命中时节省 100% | 大多数模型的缓存读取价格为输入的 0.1 倍，Claude Opus 5.5 和 GPT-6.1 Sol 为 0.05 倍，Claude Fable 5.1 为 0.025 倍 |
| **正确性风险** | 近似匹配可能返回错误答案 | 无：模型仍会生成新答案 |
| **最适合** | 答案稳定的重复问题 | 较长的共享前缀：系统提示词、工具、文档 |

深度提示词缓存折扣缩小了语义缓存在输入占主要成本的工作负载中的优势：如果请求成本大多来自较长的共享前缀，供应商缓存已经在无漂移风险的情况下省去 90% 以上的这部分费用。只有当**输出 token 或延迟**占主导时，语义缓存仍有明显优势，因为只有响应缓存会完全跳过生成。

## 语义匹配流程

1. **Embed**：将输入查询转换为向量（例如使用 `text-embedding-3-small`）。
2. **Search**：按租户和权限范围过滤后，在缓存中搜索最近邻。
3. **Threshold Check**：如果 `distance < 0.05`（非常相似），则返回缓存结果。
4. **LLM Verification**：对于高风险查询，使用较小的“Verifier Model”（例如 GPT-6 Luna、Claude Haiku 4.5、Gemini 3.8 Flash）检查缓存响应是否真正回答了新查询。
5. **Update**：如果未命中，则调用 LLM 并将新结果存入向量缓存。

**缓存键必须包含访问范围。** 根据用户 A 的文档、权限或记忆生成的响应，无论问题多相似，都不能提供给用户 B。应按租户划分缓存（如果答案取决于访问权限，还应按权限集合划分）；除非按用户分区，否则不要缓存包含个人数据的响应。

## RedisVL 和 GPTCache

标准技术栈：
- **RedisVL**：在 Redis 实例内直接提供低延迟向量搜索。
- **Hybrid Caching**：同时使用 Redis 存储元数据（键）和向量负载（vector payloads）。
- **TTL**：语义缓存应设置 TTL（Time-To-Live）。常见模式是**动态 TTL（Dynamic TTL）**：热门答案保留更久，而“stale”信息会定期被淘汰。
- **变更时失效**：按模型 ID、系统提示词版本和源数据版本管理缓存，避免提示词或文档更新后仍返回旧版本生成的答案。

## 评估：命中率与语义漂移

应像评估分类器一样评估缓存，因为每次命中都相当于预测两个查询等价：

| 指标 | 含义 |
|--------|-------------------|
| **命中率** | 从缓存服务的请求占比，体现节省收益 |
| **误命中率** | 缓存答案对新查询有误的命中占比；通过抽样并由评审模型或人类评分测量 |
| **命中与未命中的延迟** | 未命中时，在 LLM 调用之外还要支付嵌入与向量检索的成本 |
| **过时率** | 底层数据变化后仍由缓存服务的命中占比 |

应在有标注的查询对集合（等价与不等价）上，将阈值调到产品可接受的误命中率，再看命中率会落在哪里。一个命中率 40%、误命中率 0.1% 的缓存，比命中率 70% 却有 5% 错答的缓存更好。

## 多模态语义缓存

随着原生多模态前沿模型（Gemini 3.8 Flash、GPT-6.1 Sol、Claude Opus 5.5）的出现，我们现在会缓存**图像和音频查询**。
- **视觉相似度**：如果先前处理过语义相似的图像，则缓存该图像的描述。
- **音频指纹**：为相似语音指令缓存转写文本（transcripts）。

## 面试问题

### Q: 缓存中的“语义漂移（Semantic Drift）”是什么，如何防止？

**强回答：**
当相似度阈值过宽时，就会发生语义漂移，例如 0.8 而不是 0.95。像 *"How do I fix my car?"* 这样的查询，可能会匹配到 *"How do I wash my car?"* 的缓存响应。为防止这种情况，我们使用**多阶段验证（Multi-Stage Validation）**：1）向量相似度检查，2）**实体匹配检查（Entity-Match check）**（确保两个查询都涉及“Car”且动词相同），3）**阈值收紧（Threshold Tightening）**：对于技术或医疗查询，我们要求相似度 $>0.98$ 才返回缓存结果。我们还会持续抽样命中结果并评分，使误命中率成为被追踪的指标，而不是凭空假设。

### Q: 为什么在低流量下，语义缓存有时反而比原始 LLM 调用更贵？

**强回答：**
因为每个请求无论命中与否，都要支付缓存本身的开销：一次嵌入调用和一次向量搜索。嵌入几乎免费（`text-embedding-3-small` 每 1M token 收费 $0.02，因此一个 50-token 查询约需百万分之一美元），但搜索会增加延迟：进程内通常为 5 至 20 ms，跨网络则更长；还要考虑运行和维护缓存的成本。命中率低时，大多数请求付出这些开销后仍要调用 LLM，所以延迟中位数会变差，节省也很少。再算上误命中风险和工程成本，语义缓存只有在重复流量的**高规模（High Scale）**下，命中率足以抵消“Embedding Tax”时，才是明确的收益。

### Q: 已经使用供应商提示词缓存，还应增加语义缓存吗？

**强回答：**
取决于成本集中在哪一部分。提示词缓存以普通输入价格的 0.1 倍或更低价格提供重复的输入前缀，且没有正确性风险；因此，对输入成本占主导的 agent 工作负载，它已经取得大部分节省。语义缓存完全跳过调用，所以当输出 token 和延迟占主导、问题又会重复时才划算，例如客服 FAQ、产品查询和文档问答。我会先检查流量：聚类一周的查询，在满足可接受误命中率的阈值下估计命中率，并将预计节省与漂移风险、按租户分区的工作量比较。常见结果是只对狭窄且高流量的意图使用语义缓存，其他地方使用提示词缓存。
